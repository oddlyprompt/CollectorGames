# Rift Parade: integration handoff for CollectorGames

**Status: nothing here is integrated.** Rift Parade lives in `tools/rift-parade/` and `design/tcg3/` on the branch `feature/rift-parade`. No file under `src/`, `tools/build.py` or any existing game was touched. This document says how the tested rules and card data could later be connected, so that the work can be done without redesigning the game. Nothing below has been built.

## 1. What exists and what each file is for

| File | Role | Integration use |
|---|---|---|
| `design/tcg3/source/RP01_*.csv/json/md` | The production pack, unchanged | The creative canon. Never edited by gameplay work. |
| `tools/rift-parade/cards.js` | Mechanics of the 130 cards, merged with the pack's identity | The one source of truth for gameplay data. |
| `design/tcg3/cards.json` | Generated, machine-readable cards (identity, gameplay, generated rules text, purpose, alternate printings) | What a manifest or the shell should read. Regenerated by `node tools/rift-parade/docs.js`; `--check` fails if stale. |
| `tools/rift-parade/rules.json` | Every tunable rule number (deck size, Resolve, draw, Rift, compensation) | Version it with the cards. |
| `tools/rift-parade/engine.js` | The rules engine (CommonJS, no dependencies, deterministic from a seed) | Needs a thin browser wrapper (section 3). |
| `tools/rift-parade/ai.js` | Computer players (look-ahead "balanced", "aggro", "control", "greedy", "random") | NPC opponents and tournament simulation. |
| `tools/rift-parade/decks.js` | Eight representative decks | Seed for a metagame "field". |
| `tools/rift-parade/sim.js`, `report.js`, `audit.js`, `check.js` | Balance and verification tools | Keep running them after any card change. |
| `design/tcg3/rules.md`, `CARDS.md` | Rule book and generated card reference | Player-facing help text. |

## 2. Data contract with the collecting simulator

The collecting systems (pack opening, marketplace, collection, The Hunt) need only these facts about a card, all in `cards.json`:

* `id` (`RP01-001`..`RP01-130`) is the stable card identity. Wildkin uses `cid`, Tidemark `card_id`; map to whichever the shared collection code expects.
* `name`, `rarity` (`C`, `UC`, `R`, `SR`, `SEC`), `type`, `episode`, `character`, `art`: from the pack.
* `alternatePrintings`: the pack's 17 alternate printings (16 alternate art plus the hidden Episode Break) as printing ids such as `RP01-116-EB`. **A printing is a collectible, not a different gameplay card**: the engine has no entries for printing ids, and a deck is a list of card ids. Anything that stores a deck must store card ids, not printing ids, so that an alternate-art SR and the base SR are interchangeable in play.
* `gameplay.copiesMax`: 3, or 1 for the two Secret Rares.
* The pack has 130 numbered cards and a rarity distribution (48/36/30/14/2). Pull odds, pricing and the Episode Break's hidden status are not decided here and belong to the existing pack-opening and market code.

Deck legality for any importer: `E.validateDeck(ids)` returns a list of problems (empty if legal): 40 cards, per-card copy limit.

## 3. Running the engine in the browser

The existing games are one global script built by `tools/build.py` from a fixed file list (Wildkin's rules engine is `src/engine/tcg_rules.js`, global `WKR`, usable in Node and the browser). Rift Parade's engine is written as CommonJS modules (`require`) so that it could be tested headless. A browser build needs:

1. A small bundling step (for example an `esbuild`-free concatenation like `build.py`, or wrapping each file in a function and exposing `RPR = {engine, cards, ai, decks}`). The modules use only plain JavaScript: no Node APIs except `fs`/`path` in `cards.js` (reads the production JSON; replace with an inlined copy of `cards.json` for the browser) and `structuredClone` is **not** used (the pilots use `copyGame`).
2. A new entry in the build lists (a `rift` game next to `sports`, `comics`, `tcg`), or a fourth set inside the existing card-game shell if the platform direction (`design/platform-direction.md`) is followed. Decide this before writing code.
3. Per-set data (`WK_SETS`-style) generated from `cards.json` rather than read from disk at runtime.

The engine is deterministic: `E.play(deckA, deckB, seed, [agentA, agentB], opts)` always produces the same game. The whole state is plain data, so a game can be saved in the same IndexedDB slots (`src/shell/saves.js`) by serialising `g` without the non-enumerable agents (`g.ag`).

## 4. Where Rift Parade could plug into the game systems (not implemented)

* **A play screen**: a UI over `E.actionList(g, p, window)`, `E.applyAction`, `E.attackersOf/blockersOf` and the agent interface in `ai.js` (a human agent only has to answer `main`, `attack`, `block`, `react`, `choose`, `mulligan`). `cli.js` is a complete text implementation of exactly that, including the reaction window and choice prompts.
* **A metagame** (like Wildkin's): the engine can play any two decks, so a field of decks, weekly shares, tournaments and bans can be driven by `sim.js`-style matchups, precomputed at build time (compare `tools/wildkin_meta.js`). Use the "balanced" pilot for the field so that weak human decks do not distort it.
* **Card value from play**: `sim.js` produces per-card play rates and win rates; these are the same kind of signal as Wildkin's "play value comes from how much the simulated decks use a card". The data is in the JSON output (`played`, `slipped`, `trig`). Pricing itself was out of scope.
* **Rotation and future sets**: all rule numbers are in `rules.json`; abilities are data (`st`, `rule`, `tr`, `tick`, `act`) interpreted by a fixed set of ops in `engine.js` (`OPS`). A new set only needs card data unless it needs a new op; the card audit (`audit.js`) shows what each ability needs to be exercised.

## 5. Integration risks and how to handle them

| Risk | Handling |
|---|---|
| Rules numbers change after more play-testing | They are in `rules.json`. Re-run `sim.js` and `check.js`; regenerate `cards.json` and `CARDS.md`. |
| A card change invalidates saved decks | Decks are lists of card ids, so a save survives stat changes. A removed card would not; do not remove ids. |
| The pilots are not human | All balance data comes from search pilots (see the balance report's limits). Treat the field's decks as *evidence*, not truth. |
| Browser performance of the look-ahead pilot | A game costs about 0.3 s of look-ahead per full game on one core in Node; a Web Worker is advisable. The "greedy" pilot is nearly instant for bulk simulation. |
| Hidden information in copied states | The pilots copy the full state (including the opponent's hand) to search; they do not read it. A networked or competitive build would need a determinisation step. |
| Art/identity drift | Identity fields come only from the production pack; `check.js` compares every name, rarity, type, episode and art direction against the CSV. |

## 6. Suggested next steps for whoever integrates

1. Decide the home (own game, or card-game platform) and how decks are stored (card ids).
2. Generate a manifest from `cards.json` the way `tools/tidemark/checklist.py` produces `tidemark-production/manifest.json`, with printings and the hidden Episode Break.
3. Wrap the engine for the browser; reuse `cli.js`'s prompts as the interaction model.
4. Build a play screen first, then the metagame and tournaments on top of `sim.js` data.
5. Run a human playtest (see `playtests/` for the Claude-played sessions and their limits) before treating the numbers as final.
